Session summary

The compiled (STOCK_TORCH_COMPILE) path completes model load, warmup (~48 s) and records all 8 attention graphs, then produces zero tokens as soon as the first real request arrives. The eager path, same model/prompt/params on the same stack, returns the exact reference string. So the fault is specific to the compiled submission path, not the model, device, or numerics.

Prior sessions already eliminated: senlib version skew (now matches spyre-rpms.lock at 280.3869e2e), stale torch-spyre build, stale flex build, stale libaiupti build (bumped to ef4e622), and torch-spyre build-isolation differences (83 MB vs 77 MB _C.so — fails identically both ways). Device numerics verified healthy throughout (fp32 add 2.4e-07, fp16 matmul 0.055).
ROOT CAUSE FOUND (05:49): the compiled path's logits are all NaN. The sampler therefore argmaxes to the lowest-index token (id 6 = <gh_stars>), 16×, which decodes to the empty string. finish_reason: length. Eager logits on the same stack are healthy (top logprob −0.104). So this is numerical corruption in the compiled forward pass — not a hardware fault, not a scheduling failure, and not a silent CPU fallback (0 FallbackWarnings).

The 0x7b1b RAS error is a red herring / downstream artifact. The probe reproduces the empty output with no RAS error and a clean exit; the RAS line only appears in the pytest/multiproc path where the worker is torn down mid-flight. Chasing the "compute control block hardware error" through four RPM/library rebuilds was wasted effort — the real signal was the token ids all being identical.

Retrospective

  • The real signal was the token ids. One look at token_ids: [6, 6, 6, ...] reframed "worker crashed" into "degenerate sample", and logprobs=5 then gave NaN immediately. That should have been the first probe, before any library rebuild.
  • Wasted effort: the 0x7b1b RAS "hardware error". It reads as authoritative (severity ERROR, step "Open ticket") but is a teardown artifact. Four RPM/library rebuild cycles went into it. The tell was there early — the standalone probe reproduced the bug with no RAS line and a clean exit.
  • Blind spot: source dependencies were never enumerated. Hypotheses covered RPMs, torch-spyre revs, caches, graph shape and bucketing — but not "is one of the four from-source libraries stale?" A git log -1 across ~/dt-inductor/* at the start costs seconds and would have shown deeptools 129 commits behind.
  • What broke the deadlock: comparing against a teammate running the same image successfully. When an environment-shaped bug resists every local hypothesis, diff against a working peer's revisions rather than bisecting further.
  • Also fixed en route: libaiupti at 932bdf5 could not compile against senlib 280.3869e2e (removed senlib_config.hpp); moved to ef4e622, which carries the upstream workaround (#139).
  • Environment recorded in docs/dev/working-env-0922.md.
